# Building release drafts

All distribution artifacts are built through GitHub Actions after a reviewed pull request merges into main. Ordinary development/PR checks do not package releases. GitHub Releases is the first download channel; package-manager submissions follow verified assets. Source metadata alone does not publish a release.

Merges changing only root Markdown files (including README, ROADMAP and AGENTS) or files under `docs/` skip the entire release workflow through its `paths-ignore` filter. They need no version bump. The optional signer consequently has no completed release run to follow. Mixed changes, application code, dependencies, artwork and workflow/build configuration still trigger normal release validation and require an available version. Ordinary CI remains enabled for documentation changes. See [GitHub path-filter semantics](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#onpushpull_requestpull_request_targetpathspaths-ignore).

## Always-available unsigned path

`.github/workflows/release.yml` accepts only a merged `pull_request_target.closed` event into main. It validates repository, exact merge SHA, checkout, main ancestry, SemVer/name and tag conflicts before packaging. Direct pushes, tag pushes, open/unmerged PRs and manual dispatch cannot trigger distribution. Every package uses the validated SHA.

GitHub-hosted runners build Windows x64 NSIS/ZIP, macOS arm64 DMG/ZIP and Linux x64 AppImage/DEB/tar.gz through `electron-builder.unsigned.mjs`. Filenames explicitly include `unsigned`; these jobs need no signing environment, Azure account or Apple secret. macOS arm64 uses an ad-hoc signature, without a trusted Developer ID identity or notarization. Do not describe these artifacts as publisher-signed.

The validated macOS packaging step explicitly enables electron-builder signing for the merged-PR event so it applies the configured ad-hoc identity (`-`), then verifies bundle integrity before uploading. Without this setting electron-builder skips signing for the PR event and leaves a renamed Electron bundle with an invalid resource seal. This does not enable a trusted signing identity or require any certificate secret.

Leave certificate-link variables unset in this unsigned workflow. An empty `CSC_LINK` is treated as a certificate file path by electron-builder, rather than as a disabled certificate. Actions secrets are not injected into the environment unless explicitly referenced; this workflow references none.

After all unsigned targets succeed, the workflow creates a **draft** release targeting the merge SHA, reserving the intended version tag with unsigned assets and `SHA256SUMS.txt`. The Git tag itself is created when the draft is published; before publication, verify the draft target SHA instead of expecting a tag ref. Existing releases/assets are never overwritten. The workflow also saves a small release-context artifact (commit/tag/version), retained seven days, for the optional follow-up. Keep main/tags protected and normal Checks required. The workflow must exist on the default branch for its trigger to work.

The maintainer has explicitly authorized **1.0.0 Ackbar as unsigned**. Signing begins with the planned **1.0.1**, which has no release name under the patch naming rule. Do not bump the package until preparing that release's code. The first draft build succeeded on all three hosted targets; all seven downloaded checksums passed and the packaged macOS app passed a local session-only capture smoke test. Clean-machine installation still needs acceptance.

## Optional signed Windows path, from 1.0.1

Release 1.0.1 was published with maintainer authorization on 2026-10-23. Unsigned run 39955773639 and signing run 39956622696 attempt 6 succeeded from commit 7b8ff2f. WIN_MBA passed all 97 unit tests and verified valid timestamped app/installer Authenticode signatures, exact publisher and ZIP equality before upload. All nine downloaded package checksums match. The runner service uses the signing account with PowerShell 7 and Git visible on PATH; restart the service after tooling/PATH changes. Detailed clean-machine signed install/upgrade/uninstaller acceptance remains unrecorded.

`.github/workflows/release-signed.yml` follows a successful Build release draft run through `workflow_run`. It has no manual/push/PR-head distribution trigger. The hosted preflight validates the original workflow event/path/repository, checks the context commit is an ancestor of main, and reads version metadata from that exact commit. The parent release workflow accepts only a merged main PR and checks out its immutable merge SHA. GitHub reports the PR head branch in workflow_run metadata, so that field is not used as proof of the signed source.

Enable with repository variable `WINDOWS_SIGNING_ENABLED=true`. Add repository secret `SIGNING_RUNNER_READ_TOKEN`: a fine-grained token limited to this repository with **Administration: read**, used only by the hosted preflight to list repository-visible self-hosted runners. Missing token, inventory errors, missing/offline/busy runners, disabled signing or version 1.0.0 mean no signed job. Required labels are `self-hosted`, `Windows`, `X64`, `codesign`, matching the maintainer's existing signing runner convention. Ensure an existing runner is actually available to QueueCumber, rather than registered only to another project. See [runner inventory permissions](https://docs.github.com/en/rest/actions/self-hosted-runners).

Only the trusted hosted prepare job has contents: write (plus actions: read), because GitHub hides draft releases from identities without push access even when the list endpoint permits reading public releases. The workflow's default token remains read-only. See [draft visibility](https://docs.github.com/en/rest/releases/releases#list-releases).

The preflight finds the intended release by listing releases, because an unpublished draft may have no Git tag ref and cannot be resolved through the by-tag API. Tag existence is checked through git/ref/tags first: GitHub returns 404 for a missing ref but 422 when a missing name is queried as a commit. Existing tags resolve through the qualified refs/tags name, including annotated tags. Only absence of the ref is accepted; other API failures stop signing. A draft must target the exact merge SHA; any existing tag must also resolve to that SHA. A published release requires that exact Git tag commit. The release's numeric ID is passed into the signer and the same release/tag/source binding is checked again before upload. Assets are uploaded directly to that verified numeric ID, without resolving the destination again by tag or overwriting existing assets. The same draft can therefore receive signed variants before publication; changing its target or renaming it stops attachment.

The dedicated Windows runner needs tooling-download access, PowerShell 7, GitHub CLI and the certificate/private key accessible through the Windows certificate store to the runner's service account. Reuse the settings from the maintainer's supplied action:

| Repository variable | Meaning |
| --- | --- |
| `CODESIGN_CERT_SUBJECT` | Exact certificate Common Name / issued-to name, used for store selection and publisher verification |
| `CODESIGN_TIMESTAMP_URL` | Your provider's HTTP/HTTPS RFC 3161 timestamp endpoint |

These replace the earlier unverified thumbprint/publisher placeholders. The workflow bootstraps Node before pnpm, with setup-node package-manager auto-caching disabled until pnpm exists; no preinstalled Node is required. The config `electron-builder.self-hosted.mjs` selects the certificate by subject, forces signing, requests SHA-256 plus RFC 3161 timestamping, and gives assets distinct signed filenames. No PFX export/password, Azure account or private key in GitHub Secrets is needed. A hardware-backed key can work when its installed provider exposes the certificate to SignTool; validate PIN/service-account behavior on the actual runner. Do not assume every HSM backend works.

Application and installer Authenticode signatures must be Valid, timestamped and match the configured certificate CN. The signed ZIP must contain a byte-identical copy of that verified application executable. Only then are the signed Windows installer/ZIP and `SHA256SUMS-signed-windows-x64.txt` attached to the same release, without clobbering unsigned files or publishing the draft. Test the installed uninstaller during real acceptance; local mocks do not certify it. A signing error leaves unsigned output intact. A failed upload can leave a subset of already verified signed files, which must be inspected before publication. macOS trusted signing/notarization and Linux package signing remain outside this Windows path.

Availability is a snapshot, not a reservation. The existing hosted watchdog allows two minutes for the signer to start, then cancels only the isolated optional workflow if it is still observed queued. If the jobs API remains unavailable or state is unknown, it fails visibly without cancelling a potentially active signer; manually inspect any remaining queued job. A start concurrent with cancellation remains possible. Signing has a 30-minute execution timeout. The unsigned release workflow has already finished and is never cancelled by this watchdog. See [workflow cancellation](https://docs.github.com/en/rest/actions/workflow-runs#cancel-a-workflow-run).

Use a dedicated, preferably ephemeral runner restricted to trusted release work. Clean checkout precedes each run; keep keys outside the workspace and never run arbitrary PR code on this machine. Inventory authorization does not grant signing-key access. Real signing/upload passed for 1.0.1. The remaining unavailable-runner/watchdog acceptance cases are tracked in ROADMAP.md.

## Version names and publication

Tags and filenames stay numeric SemVer. Major/minor releases with patch zero use `releaseName`: Star Wars characters with A for major 1, B for major 2, through Z. **1.0.0 is Ackbar**; patch releases such as 1.0.1 omit the field. Automated validation enforces the letter/Ackbar/absence rules; character authenticity remains reviewable content.

Review downloaded checksums, install/upgrade/uninstall behavior, actual supported architectures and signing status. Verify the signed app and installed uninstaller when signed variants exist. Unsigned artifacts must remain clearly labeled; expected OS warnings are not evidence of a valid publisher signature. Do not disable system-wide security protections to pass acceptance. Use [prepared notes](RELEASE_NOTES_1.0.md) and [acceptance checklist](ACCEPTANCE.md), then publish the draft deliberately. Neither workflow automatically publishes or submits package-manager manifests.
